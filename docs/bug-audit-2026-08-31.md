## Fixed

### 1. Follow-ups could reach people who had opted out — `src/lib/followup.js`

The worst of the three, and a repeat of a bug already fixed **on the broadcast
path in August but never on this one**. Follow-ups reach the same people,
through the same 24-hour window.

Four reads decide who to *exclude*: who replied since, who was already followed
up, who opted out or paused the bot, and who already ordered. Each was read as
`(q.data || [])`. A failed read therefore produced an empty exclusion list,
which is not "nobody matched" — it is "we do not know" turned into permission
to send:

```js
const c = contact.get(senderId);
if (c?.broadcast_opt_out) continue;   // no row → undefined → sends anyway
```

They run in one `Promise.all`, so **one failing while the others succeed is the
ordinary case**, not a rare one. Nothing threw and nothing logged.

Every read now checks its error and the run stops with `skipped: "read_failed"`.

*(One read already failed safely: no tags means nobody is "interested", so a
total outage sent nothing. That is why this never showed up.)*

### 2. Contact lists were silently truncated — `src/lib/page.js` (new)

PostgREST caps an unbounded `select` at `db-max-rows` and answers with a normal
200 and a short array. `/api/contacts` and `/api/conversations` both read
`contacts` unbounded, so a client with more contacts than the cap was shown a
list quietly missing people — no error, no flag, no way for the screen to know.

`pageAll()` reads by range until a page comes back short, **throws** on a failed
page rather than returning what arrived, and reports `truncated` at a hard
ceiling. The contact list now returns an error rather than a short list; the
inbox falls back to un-named conversations, which is still readable.

There is a second `pageAll` in `api/admin/packages/route.js`. It is not a
duplicate to be merged: it *returns* the error so the panel can draw a partial
month and say so beside it, which is the right answer there and the wrong one
for a client's own contact list.

### 3. A failed usage count read as "you have used nothing" — `/api/billing`

`usageThisMonth` and `usageToday` returned `count || 0` with no error check, on
the screen an owner uses to decide whether to upgrade. A failed count drew an
**empty progress bar** for somebody sitting at their limit. Both return `null`
now, `pct` is null rather than 0, and the tab shows `—`.

## Raised and dismissed

Kept here so the next audit does not re-open them.

- **`channels` read without `client_id`** (`bot.js`, `widget/chat`) — a webhook
  arrives with a page id and no client; finding the client IS the lookup.
- **`broadcast_recipients` without `client_id`** — claimed by primary key, and
  the id came from a read already scoped to the client.
- **`.eq(col, null)` in `bot.js:427`** — the comment explaining the fix, not the
  bug.
- **Unbounded `channels` / `file_registry`** — both capped by the package
  (3 channels, 40 documents) long before any row limit.
- **`bot.js` message-quota `count || 0`** — deliberate and documented: a
  customer's reply must not be withheld because bookkeeping failed.
- **`followup.js` reads with `.in(ids)`** — `ids` comes from a `.limit(500)`
  read, so the list is bounded.

## Not covered by this sweep

Stated so the gap is known rather than assumed away:

- Anything needing a live database or a real AI key. Local `.env.local` holds
  placeholder Supabase credentials.
- Meta webhook delivery, OAuth redirects, cron — none reachable from localhost.
- Race conditions and anything timing-dependent.
- **The test suites themselves live in a scratch directory outside the
  repository.** They are not version-controlled, they are not run by CI, and
  they can be lost. That is the largest known fragility in this project's
  testing and it is not a code bug.
