# Bug audit — 2026-08-15

Full-project sweep for real bugs (not style). Focus: tenant isolation (`client_id`
filtering at the DB), the `bot.js` reply engine, API routes, the broadcast/follow-up
24-hour window, and general runtime bugs (null access, missing awaits, off-by-one).

Severity: **high** = data leak, data loss, or a customer-facing failure; **med** =
wrong result under load or at scale, no leak; **low** = cosmetic / minor.

---

## Tenant isolation (`client_id` at the DB)

This is the same anti-pattern already fixed once in `src/lib/bot.js` on 2026-08-07
(see `memory.md` and `lessons.md` #14): fetch rows with `select("*").limit(N)` across
**all** tenants, then filter down to one tenant in JavaScript. Two problems every time:
the DB does the filtering only after transferring every tenant's rows to the server
(the stated invariant — "every query filters `client_id` at the database with `.eq()`"
— is broken even when nothing leaks to the client), and once total row count across
all tenants passes the hardcoded limit, a busy tenant's own rows can silently fall
outside the window and vanish from their own dashboard.

`lessons.md` #14 already predicted this: "grep the whole repo for the same shape
before calling it done" was written down and not done. This audit is that grep.

### 1. `src/app/api/me/route.js:39` — high — FIXED
`message_buffer.select("id,client_id,role,created_at")` had **no `.eq()` and no
`.limit()` at all** — every call to `/api/me` (fired on every dashboard load, by
every tenant) pulled the *entire* `message_buffer` table into server memory just to
count one tenant's messages sent today. Fixed to a DB-side `count` query scoped by
`.eq("client_id", ...).eq("role","customer").gte("created_at", today)`, matching the
identical pattern already used for the same purpose in `bot.js`'s `dailyLimitReached`.

### 2. `src/app/api/contacts/route.js:10` and `:17` — high — FIXED
`contacts.select("*")` and `message_buffer.select("sender_id,role,client_id,platform")`
— both **unbounded, no filter** — ran on every load of the Conversations tab's contact
list. Fixed with `.eq("client_id", client.id)` (and `.eq("role","customer")` on the
message read, dropping the now-redundant JS filter).

### 3. `src/app/api/orders/route.js:10` — high — FIXED
`orders.select("*").order(...).limit(300)` with no `client_id` filter — the newest 300
orders **across every tenant**, filtered down in JS. This is exactly the `pendingFor`
bug already fixed in `bot.js` on 2026-08-07: once other tenants' orders fill the
300-row window, a tenant's own recent orders disappear from their Orders tab with no
error. Fixed to `.eq("client_id", client.id)` before `.order()/.limit(300)`, so the
limit now applies per-tenant.

### 4. `src/app/api/products/route.js:10` — high — FIXED
`products.select("id,metadata,client_id").limit(1000)`, no `client_id` filter — the
product list a business owner sees in Inventory. Same failure mode as #3: once total
product rows across all tenants exceed 1000, some tenants' own products stop appearing
in their own product list. Fixed to filter by `client_id` before the limit.

### 5. `src/app/api/import-one/route.js:46` — high — FIXED
Same table, same missing filter, used for **duplicate detection** on product import:
fetches up to 1000 products across all tenants, then looks for the tenant's own
existing row with a matching `product_code` to replace. Once other tenants' rows fill
the 1000-row window, the duplicate is never found, so re-importing a product silently
creates a second row instead of replacing the first. Fixed to filter by `client_id`
before the limit, and the duplicate-detection logic no longer needs the redundant JS
`client_id` check.

### 6. `src/app/api/profile/route.js:48` — med — FIXED
`channels.select("id,client_id").limit(500)`, no filter — used only to compute the
"channels connected" usage number shown in Profile. Wrong count once total channel
rows exceed 500, no data-loss risk (it's a display number, not a list). Rewritten as
a DB-side `count` query, matching the pattern already used two lines above it for
`products`/`orders` usage in the same function.

### 7. `src/app/api/channels/route.js:10` — med — FIXED
`channels.select("*").order(...)`, no filter and no limit — fetched every tenant's
channel rows (including `access_token`, stripped only in the response mapping) on
every Channels-tab load. No token leak to the browser since the field is dropped
before the response, but still an unbounded cross-tenant fetch on the busiest tab in
the dashboard, and it will only get slower as tenants grow. Fixed to
`.eq("client_id", client.id)`.

### 8. `src/app/api/send-message/route.js:13,16` and `src/app/api/send-media/route.js:15,17` — med — FIXED
Both routes power "reply from the dashboard": they look up which platform a customer
last messaged on and which of the tenant's channels to send through. Both queries
fetched **all tenants'** rows (`message_buffer.limit(300)`, `channels.limit(200)`),
filtering down in JS. Two failure modes: (a) once other tenants' traffic fills the
300/200-row window, the lookup can miss and silently fall back to `"facebook"` /
"no connected channel", so a reply meant for WhatsApp could be attempted on the wrong
platform, or a reply could fail outright with a channel the tenant does have connected;
(b) plain inefficiency — refetching hundreds of other tenants' rows on every single
dashboard reply. Fixed by scoping both queries with `.eq("client_id", client.id)` (the
message lookup also now scopes to the one `sender_id` and takes only the newest row,
since that's all the code used).

### Checked and confirmed correctly scoped (no change)
- `src/lib/bot.js` — re-verified after the 2026-08-07 fix; all seven previously-fixed
  reads still filter `client_id` at the DB, and no new anti-pattern was introduced
  since. `getChannelByPage` (line 20) is deliberately unscoped — it resolves *which*
  tenant a webhook belongs to, so it has no `client_id` yet; this is documented and
  intentional, not a bug.
- `src/app/api/admin/route.js` — the whole-table reads at lines 50–56 are gated behind
  `callerRole(email) === "super"/"admin"` and are the admin dashboard's intended
  cross-tenant aggregation. Correctly gated, not a leak.
- `src/app/api/conversations/route.js`, `knowledge`, `comments`, `bookings`,
  `bookings/list`, `generate-prompt`, `widget/chat`, `broadcast`, `analytics`,
  `settings`, `billing`, `tags` routes, and `src/lib/broadcast.js` / `broadcast-send.js`
  / `followup.js` / `tags.js` — all filter `client_id` (or the equivalent scoping key)
  at the database on every read checked.

## General runtime bug — demo chat bot completely broken

### 9. `src/app/api/demo-chat/route.js:7` — high — FIXED
`import { languageRule } from "@/lib/bot.js"` — **`languageRule` does not exist** in
`bot.js` and never has (confirmed: `npm run build` prints "Attempted import error:
'languageRule' is not exported from '@/lib/bot.js'"). The import silently resolves to
`undefined`, and the only place it's used — `languageRule(userText)` on the line that
builds the prompt sent to Gemini — throws `TypeError: languageRule is not a function`
on *every single message*. The route's `catch` block turns that into
`{ reply: "Error: languageRule is not a function", ... }`, so the **demo bot on the
public website — the thing a visitor tries before signing up — has never returned a
real answer**, only that error text.

The intended function exists under a different name: `languageLock(lang)` in
`bot.js`, used by the real reply engine (`composeReply`) to force a reply into the
customer's detected language. It was not exported, and the demo route's import was
never updated to match — most likely a leftover from the language-mode fix done on
2026-08-07 (`memory.md`, `lessons.md` #15), which touched this exact mechanism in
`bot.js` but not this caller.

Fixed: exported `languageLock` from `bot.js` (one word), and in `demo-chat/route.js`
imported both `detectLanguage` and `languageLock` and called
`languageLock(detectLanguage(userText))` — the same two-step pattern `composeReply`
already uses. Confirmed the import warning is gone from a clean `npm run build`.

## Broadcast / follow-up — Meta's 24-hour window

Verified, no bug found:
- `src/lib/broadcast.js`: `WINDOW_HOURS = 24`; `resolveAudience()` computes
  `windowCutoff = Date.now() - WINDOW_HOURS * 3600 * 1000` and skips anyone whose last
  inbound message is older than that, with the reason `SKIP.window` shown per
  recipient in the preview.
- `src/lib/followup.js`: `SAFE_WINDOW_HOURS = WINDOW_HOURS - 0.5` (23.5h) and
  `MAX_DELAY_HOURS` caps the configurable delay below the 24h line, anchored on the
  customer's own last inbound message — not a fixed clock time — so a slow run can
  never push a send past the window. This matches the design written up in
  `memory.md`'s 2026-08-07 entry and was re-checked against the current code, not
  assumed from that note.

## Not fixed — needs owner input or a bigger change

Nothing found in this sweep required a large or risky change. Everything identified
above was small enough to fix directly (the same one-line-`.eq()` pattern already
proven safe on 2026-08-07). If a future sweep finds something structural — e.g. the
300/500/1000 "global limit" numbers recurring elsewhere as the codebase grows — the
right long-term fix is a lint rule or a shared query helper that makes an unscoped
`client_id` read impossible to write by accident, rather than catching each one by
hand. Flagging as an idea, not doing it now — it is bigger than this task.
